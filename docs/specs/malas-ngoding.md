# Malas Ngoding: 3D energy digital twin of Kalimantan Timur

Design spec, 20 Oct 2026. Team and app name: **Malas Ngoding**.

## Why

Entry for the INSEVENT 2026 Fullstack Web Development Competition (Sistem Informasi, Universitas Mulawarman), subtheme **SDG 7, Integrated Clean Energy Ecosystem**. Submission deadline: **25 Oct 2026, 23.59 WITA**.

Most of Kaltim's electricity comes from coal. Ordinary people cannot see how much CO2 their buildings cause, or what moving to rooftop solar would change. Malas Ngoding is an interactive 3D map that makes this visible and understandable for anyone, and gives local government data-driven recommendations.

Scoring this design optimises for:
- First round: innovation 30%, UI/UX 25%, technical implementation 25%, documentation and impact 20%.
- Final: **live demo 50%**, technical depth (tech, architecture, security) 30%, presentation 20%.

So: a stunning, smooth, animated live demo comes first. Technical depth (PostGIS, caching, AI tool use) comes second.

## Goals

1. A full-screen 3D Mapbox map of Kalimantan Timur (style Mapbox Standard, terrain on). The 10 kabupaten/kota are extruded by their electricity use or CO2, coloured by intensity, hoverable and clickable.
2. **Click any building** (Mapbox Standard `buildings` featureset, via `map.addInteraction`) to see:
   - estimated yearly and monthly kWh (from footprint area x floors x intensity for the building type),
   - the grid mix behind that electricity (e.g. 70% coal PLTU, 25% gas), not one specific plant, because grid power is pooled,
   - estimated CO2 per year,
   - layman equivalents (car km, trees needed, phone charges, flights).
   Every estimated number is labelled "perkiraan".
3. **Solar simulation** for the selected building: roof area -> kWp, yearly production (NASA POWER irradiance), share of demand covered, battery size for N hours of backup, cost, payback years, CO2 avoided.
4. **Weather-aware solar prediction**: Open-Meteo forecast for the next days, predicted PV output per hour/day, with rain and cloud lowering output. The map shows a live rain effect (`map.setRain`) when it rains at the view centre, and the light preset follows the real time of day in WITA.
5. **Power plants layer**: major Kaltim plants as 3D markers coloured by fuel, sized by MW.
6. **Recommendations for government** per kabupaten/kota (sustainable development and spatial planning), generated by Claude from the region's data and cached in the database, with a rule-based fallback.
7. **AI chat** (Anthropic API, model `claude-sonnet-5-5`, no rate limit) that answers questions about the map and **drives the map**: fly to a region, select a building at a place, toggle layers, run the solar simulation, toggle rain. Map actions are tool calls that the client executes.
8. **Animations everywhere** ("kita main di animasi"): intro fly-in from globe to Kaltim, regions rising, smooth camera moves, panel transitions, animated counters and charts, hover glow, slow orbit when idle.

## Non-goals

- No real metered data, IoT or sensors. All per-building numbers are model estimates.
- No user accounts or login.
- No deployment yet (Railway later, after the user reviews). The app must still be deploy-ready (Dockerfile or simple start command).
- No mobile-first layout; desktop and laptop for judges come first, but the layout must not break on a tablet.

## Anti-goals (failure even if it works)

- A demo that stutters, shows blank panels, or throws errors in the live demo.
- Numbers that look invented without a source or method. Every factor must trace to `docs/research/*.md` or be marked as an assumption.
- AI chat that hallucinates numbers: the chat must get numbers from tools that query our data.
- Any Claude/AI attribution in commits or docs.

## Constraints

- Runtime: **Bun** everywhere (server, bundler, tests, scripts). Frontend **React** + TypeScript.
- Database: **Postgres + PostGIS** in Docker for local dev, on host port **5433** (port 5432 already runs another project's container; never touch it). Access via `Bun.sql`.
- Secrets in `.env` (`MAPBOX_TOKEN`, `ANTHROPIC_API_KEY`, `DATABASE_URL`). Never commit `.env`; `.env.example` documents keys. The Mapbox public token is served to the client through `/api/config`; the Anthropic key never leaves the server.
- API routes under `/api/...` without version prefix.
- UI language: **Bahasa Indonesia**. Code, identifiers and comments in English.
- Git: branch `main` only, no PRs. Commit format `type(scope): desc` (conventional commits, lower case, e.g. `feat(map): extrude regions by co2`). No attribution trailers.
- External APIs (NASA POWER, Open-Meteo) are cached in the database so the live demo works on slow wifi; seed data ships with the repo so the app runs offline except for map tiles and Claude.

## Data and method

Research files in `docs/research/` hold the numbers and sources:
- `grid-and-plants.md`: grid emission factor, generation mix, plant list with coordinates, fuel factors.
- `consumption-by-region.md`: kWh sold, customers, population, electrification per kab/kota.
- `building-intensity.md`: kWh/m2/year per building type, OSM tag mapping, floor height, layman equivalents.
- `solar-weather-boundaries.md`: NASA POWER and Open-Meteo endpoints, PV and battery formulas, costs and tariff, ADM2 boundaries source.

Building estimate: `area_m2 = footprint area (from feature geometry, computed server-side with PostGIS or turf)`, `floors`, `kWh/yr = area_m2 x floors x intensity[type]`.

Fact check done 20 Oct (Mapbox Tilequery, `mapbox.mapbox-streets-v8`): Samarinda, Balikpapan, Bontang and Tenggarong all have dense building footprints, but every footprint has `type: "building"` and the default `height: 3`. So neither type nor height is useful from the building itself. Therefore:
- **Type** is inferred from the nearest POI (`poi_label` layer, `class`/`type`, e.g. `education/School`, `store_like/Mall`, `lodging/Hotel`, `general/Government`, `religion/Place Of Worship`) within the footprint or about 25 m of it, looked up server-side via the Tilequery API and cached. Fallback: footprint under ~250 m2 = rumah tinggal, otherwise ruko/komersial.
- **Floors**: if height is the 3 m default, use a typical floor count per type (e.g. house 1, ruko 2-3, school 2, office 4, hotel 6, hospital 4, mall 3); if a real height exists, `round(height / floorHeight)`.
- The user can override type and floors in the panel and the numbers recompute.

CO2: `kWh x grid emission factor`. Breakdown by source: `kWh x mix share x fuel factor`, normalised to the grid factor.

## Architecture (builder may refine)

- `src/server/`: `Bun.serve` with `routes` for `/api/*` and HTML import for the SPA. Modules: `db`, `regions`, `plants`, `buildings` (estimate + cache), `solar` (simulate), `weather` (forecast + cache), `recommendations`, `chat` (Anthropic streaming with tools, SSE to client).
- `src/web/`: React app. Map (Mapbox GL JS v3), panels, chat, animations (Motion for React).
- `src/shared/`: pure calculation modules shared by server and tests (`estimate.ts`, `solar.ts`, `equivalents.ts`, `emissions.ts`) and API types.
- `db/`: SQL migrations; `scripts/seed.ts` loads boundaries GeoJSON and research JSON.
- Tables (minimum): `regions` (geom, stats), `power_plants` (point), `grid_mix`, `fuel_factors`, `building_types`, `building_estimates` (cache by feature id), `solar_climatology_cache`, `weather_cache`, `recommendations`, `chat_sessions`, `chat_messages`.
- Tests: `bun test` for all pure calculation modules and API handlers (handlers with a test database or a thin db fake).
- Docs: `README.md` (local install and run, for judges), `docs/technical/` (ERD and flowcharts in Mermaid, architecture, app flow) as the source for the PDF the team submits.

## Left to the builder

Visual style (aim: modern, dark-first, energetic accent colours, readable for laypeople), exact panel layout, chart library, animation details, chat tool schema, file layout inside `src/`, and test structure. Choose sensible defaults and note them in the spec's decision log below.

## Decision log (calls made without the user, to check on review)

- Repo `akhmadqasim/malas-ngoding`, private for now. The guidebook requires a public repo at submission; switch before 25 Oct.
- Campus and team member names are placeholders in docs.
- The grid mix is shown per building instead of a single plant, because grid electricity cannot be traced to one plant.
- Research files are being produced by research agents on 20 Oct. Any value without a solid source goes in as an explicit assumption (in the seed data with `source = 'asumsi'` and shown in an "Metodologi & sumber" panel), never silently.
- **Build order** (everything in Goals is in scope; this is the cut order if time runs out, last cut first): (1) map + regions + intro animation, (2) building click + estimate + equivalents, (3) solar simulation, (4) AI chat with map actions, (5) weather forecast + rain effect, (6) recommendations, (7) power plants layer. Animation polish is part of every step, not a final step.
- Verification: builders are agents. Every step ships with `bun test` coverage for logic and handlers, plus a browser smoke check of the real app (map renders, click works, no console errors) before the step counts as done. A scripted demo path is documented in `docs/technical/demo-script.md`.
- Demo setup is one command sequence in the README: `docker compose up -d`, `bun install`, `bun run setup` (migrate + seed + warm caches), `bun dev`. The final live demo runs on the team laptop; judges in round one will use a deployed URL that the team creates later.
- Chat guardrails: max 8 tool-loop iterations per user message, `max_tokens` around 2048 per response, history kept per anonymous session id (stored in localStorage, persisted in `chat_sessions`/`chat_messages`).
- Region recommendations are generated for all 10 regions during `bun run setup` (when the key is present) and cached; a "Perbarui" button regenerates on demand. Solar climatology for each region centroid is pre-cached during setup too.
